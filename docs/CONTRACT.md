# Контракт стенда — проект, только синтетика

## Слои и цепочки

Три физические схемы GP: `oil_stg` — неизменённый конверт, batch и checkpoint; `oil_dds` — журнал + Raw Vault hubs/links/satellites; `oil_mart` — версионные измерения, отдельные факты и агрегаты. Это упрощённая модель DV с историей каждой версии; не заявляется полная реализация Data Vault 2.0, промышленный collision guard и распределённая транзакция. Количество объектов и lineage — в `metadata/lineage.yaml`; это спецификация, а не фактическая регистрация каталога.

Цепочка 1: сведения о месторождениях и скважинах + суточная добыча → `refresh_production` → `v_field_production`. Цепочка 2: простои + уже построенные факты и измерения → `refresh_downtime` → `v_field_performance`. Вторая зависит от первой, но первая не зависит от простоя. Между вызовами двух независимых транзакций GP общий dashboard может временно показывать несовместимые версии: для реального допуска нужны общий release ID, единая точка публикации или окно остановки чтения, что пока не реализовано.

## Семантика

Kafka key: `event_type:entity_id`; topic `oil.events.v1`. Поля event: `schema_version=1`, уникальный `event_id`, тип `field|well|production_day|downtime`, `entity_id`, положительная `entity_version`, `op=U|D`, `event_time` с часовым поясом, `payload`. Повтор одного события побайтно идентичен; при исправлении увеличивается версия и меняется event_id. Для удаления payload полный. Конфликт event ID и версии отклоняется; при обработке актуальной версии выигрывает максимальная entity_version. Одновременных writers в GP нет: нужен внешний fence.

`field`: `field_id, field_name, region`. `well`: `well_id,field_id,well_name,valid_from,status`; статус ACTIVE/INACTIVE, действует с даты UTC. История полей определяется event_time, скважин — valid_from; повторяющиеся effective даты отклоняются. `production_day`: `production_id=well_id_YYYYMMDD,well_id,production_date,oil_tonnes,status`; одна запись по скважине в сутки, масса в тоннах, неотрицательна; INACTIVE означает нулевую добычу. Состояние production_day обязано совпадать с измерением well на дату. `downtime`: `downtime_id,well_id,start_at,end_at,reason` (EQUIPMENT, POWER, PLANNED). В первой версии интервал целиком в одних сутках UTC; end на следующей полуночи разрешён. Пересекающиеся интервалы одной скважины отклоняются при пересчёте. Для промышленного потока доработать разбиение по дням и объединение пересечений с согласованным приоритетом причин; сейчас это не поддерживается.

Масса нефти синтетическая, в тоннах, не связана с единицами в старом baseline. `producing_well_days` — количество записей ACTIVE по well/day, при условии полноты поступления каждого дня; это прокси для дней активного фонда, не факт реальной работы оборудования. `oil_per_well_day` — масса на ACTIVE well-day, NULL при нулевом знаменателе. Без отдельного источника полноты нельзя утверждать, что отсутствующее событие означает отсутствие добычи; текущая модель не генерирует строки отсутствующих измерений. `downtime_hours` — сумма допустимых непересекающихся интервалов; недополученная нефть, прибыль и downtime_share не рассчитываются.

## Граница миграции

Система снимает GP consistent snapshot только после остановки всех источников записи, подтверждения durable Kafka checkpoint и фиксации end offsets **exclusive** по каждой partition; приемник TO BE читает от этой границы с сохранёнными retention и обработкой replay. Позиции staging fixture не являются реальными Kafka offsets. Снимки отдельных Iceberg таблиц должны быть зафиксированы по одобренной границе; все проверки и сравнение отчётов привязывают к ней. Реализация согласованного snapshot/offset и continuous CDC пока отсутствует; каталог не подтверждает корректность границы.

## Применение

Файлы `01_schema.sql`, `02_load.sql`, `03_marts.sql`, затем approved staged fixture, `apply_batch`, `refresh_production`, `refresh_downtime`, `quality/01_checks.sql` — только после проверки модели, backup, GP6 syntax, прав и отсутствия конфликтующих namespace. Операции функций — одна транзакция GP на вызов, при ошибке откат; это не транзакция Kafka и не commit между базами. Миграцию и DAG не запускать во время подготовки. Версии генератора, коннектора, SQL, offsets и результаты проверок сохранять в защищённом манифесте; секреты не записывать.

## Ключи и поздняя история

Ключи вычисляются детерминированно как MD5 от типизированного ASCII бизнес-ключа с префиксом; составные ключи отделяются двоеточиями, которые запрещены в идентификаторах. После вставок apply проверяет уникальность бизнес- и hash-ключа каждого hub, уникальность каждого link по hash и паре компонентов, соответствие исходных бизнес-ключей сохранённому hash, уникальность event_id в каждом satellite; нарушение откатывает batch. Проверка защищает от обнаруженной коллизии на имеющихся данных, не гарантирует криптографическую стойкость MD5 и не заменяет ограничения конкурентной записи. Повтор с тем же event_id и побайтно тем же JSON не создаёт новую версию; тот же event_id с иным документом и разные event_id для одного entity_version отклоняются. Поздняя меньшая версия хранится в истории; факт выбирает максимальную entity_version. Измерения используют effective time независимо от порядка приёма, совпадающие effective даты отклоняются на стадии refresh. История изменяется только добавлением, при условии запрета прямого UPDATE/DELETE привилегиями и внешнего single-writer fencing; эти права и fence должен обеспечить оператор.

Ссылочная полнота проверяется при пересчёте и DQ после поступления зависимых событий, а не в каждом single-message batch: Kafka не гарантирует порядок между разными ключами. До этого момента hub/link могут содержать ключ, для которого ещё не пришло событие родителя. Не следует публиковать неполный расчёт. Сертификация DV2.0, multi-source key namespace, обработка ошибок и перформанс на большом объёме не подтверждены.
