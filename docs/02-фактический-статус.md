# Нефтегазовый демостенд: фактическое состояние

Дата проверки: 21 ноября 2026. Данные синтетические, масса нефти в тоннах, время UTC. Документ фиксирует выполненное, а не предполагает промышленную отказоустойчивость.

## Границы и первая волна

Старые прикладные GP схемы и 46 Iceberg-таблиц удалены после резервирования. Подробности и восстановление: `../dp103-oilgas-reset-20261120/RESTORE.md`. В LakeKeeper отдельно остался ранее обнаруженный нечитаемый `og_migration.spark_literal_20261115_01`, не включённый в удаление.

Создана цепочка источника: генератор → `oil.events.v1` (3 partitions) → `webinar-oil-gp-ingest` → `oil_stg` → `oil_dds` → `oil_mart`. Начальный набор: 5 месторождений, 40 скважин, 14 600 суточных фактов добычи, 880 интервалов простоев; всего 15 525 событий. Генератор отправил их через Kafka; они доставлены в Greenplum и обработаны, без повторной отправки после исправления прав последовательности.

Перед переносом генератор завершился, source sink поставлен на паузу, Kafka exclusive offsets и GP checkpoints совпали: `[5170,5196,5159]`. GP dump SHA-256 `f1438de94415b53082c8925f2df35714f7f3e1e1cd38152517fe85cab2d8d920`, восстановлен в отдельную `og_oil_wave1_20261121`. На 13 объектах counts и суммы row hashes совпали с источником; это не криптографическое побайтовое доказательство. Из паузы источник считан Cedrus, Iceberg-таблицы созданы отдельными CTAS; витрины рассчитаны в DLH по SQL из DDS. Для 14 объектов, включая raw events, 8 DDS и 4 mart, `EXCEPT ALL` в обе стороны показал 0 различий. Манифест — `wave1-release-manifest.json`, результаты — `wave1-reconciliation.json`, фактические запросы — `wave1-sql-plan.json`.

Первая волна — только `field`, `well`, `production_day` и отчёт добычи. Вторая волна — `downtime` и отчёт эффективности — остаётся в GP; соответствующие target DDS/MART объекты и целевой поток изменений не созданы. First-wave initial snapshot есть в DLH; continuous sync пока не настроен, поэтому новые изменения GP не автоматически совпадают с DLH.

## Компоненты

- GP: `oil_stg`, `oil_dds` (учебная адаптация Raw Vault), `oil_mart` (звезда), 25 таблиц, 3 view и функции. Семь DQ-проверок вернули 0. Active well-days — прокси активности по полноте событий, не фактические часы работы. Интервалы простоев ограничены сутками UTC и без перекрытий.
- Airflow: `oil_gp_release`, ручной и paused. Проверочный запуск `oil_gp_baseline_verify_20261121` завершился success; batch уже был обработан, DAG повторно пересчитал две витрины. Пауза источника и checkpoints — внешняя проверка оператора, не автоматический fence.
- Superset: GP dashboards ID 3 и 4 и DLH-копия первого ID 5 опубликованы. Сохранённые запросы 12 графиков завершились success/done через API, есть фильтры по региону и месторождению. Визуальная проверка в пользовательском браузере и работа фильтров мышью не подтверждены. DLH dashboard читает реальную таблицу `dlh.oil_mart.agg_field_day`: SELECT из `dlh.oil_mart.v_field_production` пока возвращает PERMISSION_DENIED при текущем пользователе, хотя таблица читается.
- Data Catalog: фактически созданные GP/DLH таблицы, Kafka topic, Connect, Airflow, 3 dashboard и 12 charts зарегистрированы. Связи зарегистрированы вручную по SQL/конфигурациям; на поддерживаемых table-to-table связях добавлен column-level lineage, поля графиков описаны текстом. Полное автоматическое column lineage от JSON до всех BI полей и корректность каждой связи в UI ещё не доказаны; owner бизнеса не назначен.
- Репозитории: ncuho/dwh-greenplum-scripts и ncuho/dlh-scripts очищены от торгового кейса, содержат новый SQL/генератор и артефакты первой волны. Токены/пароли не записаны. История Git и локальные bundles сохранены.

## Что остаётся до полностью рабочего сценария вебинара

1. Построить и испытать именно целевую вторую цепочку: отдельный Iceberg Sink и staging contract, idempotent применение U/D/replay, разрешения LakeKeeper/S3, корректное переключение, обновление DDS/MART и обработка дельт. Подготовлен неисполненный `sql/wave2_migration.sql`; read-only вычисление факта простоев через Cedrus и сравнение с GP дали 0 различий на имеющемся срезе. Это не запуск и не полная проверка второй бизнес-миграции.
2. Проверить полномасштабный target DAG и Spark-код на установленном runtime; текущая первая волна реально выполнена Cedrus SQL, а не Spark. Подготовить управляемый release manifest и единый барьер публикации нескольких таблиц.
3. Устранить отказ SELECT из DLH view или официально использовать таблицу `agg_field_day` как BI-объект. Проверить роли, S3, users, Superset и физическую доступность всех компонентов в пользовательском UI.
4. Настроить реальную автоматическую/периодическую source orchestration и контроль владельца, длительного token lifecycle и ingestion lag. Текущий DAG manual, connector RUNNING, генератор не запущен. Kafka single-node RF=1 и demo sink не являются HA.
5. Проверить всю диаграмму lineage до пользовательского UI и детальный column-level coverage без ложных связей. Привязать подходящие глоссарные термины и назначить владельцев; PXF не установлен/не подтверждён и не обязателен для Kafka.
