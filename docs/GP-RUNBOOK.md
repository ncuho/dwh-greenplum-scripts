# Проверка двух цепочек на доставленных Kafka-событиях

**Выполнять только после backup, проверки GP6 и согласования оператором; этот документ не означает, что шаги выполнялись.** Нужны отдельный топик `oil.events.v1`, настроенный sink с записью `oil_stg.event_log`, `batch_control`, `kafka_checkpoint`, установленный `gp/04_coalesce.sql`, защищённые учётные записи и заранее записанные версии DDL/генератора. Источник и цепочки должны быть изолированы от используемых объектов. Реальные Kafka offsets получает только consumer; синтетические fixture позиции не используются.

## Почему coalesce и как он работает

Sink пишет событие и его исходный READY batch. При остановленном sink и обработчике `oil_stg.coalesce_ready_batches(first_id,last_id,new_id,source,max_events)` выбирает только READY batch указанного source в границах id, ограничивает число событий, атомарно создаёт новый batch, сохраняет связь исходных batch и каждой реальной тройки `(topic,partition,offset)`, переносит записи по batch_id, ставит исходным COALESCED, новому READY. Тройка Kafka, JSON, дата получения и checkpoint не меняются. Список может содержать пропуски, исходные IDs — не Kafka offsets; `min/max` не подтверждают полноту.

Обязательна реальная остановка Kafka sink **и всех** процессов apply/coalesce на весь момент транзакции либо единый внешний lock/fence, который реально соблюдают все writers. Сам SQL lock не создаёт; проверки количества не являются защитой от всех гонок. Параллельно нельзя вручную менять события, статусы и маппинги. `new_id` резервируется из того же источника уникальных batch IDs, что sink (`oil_stg.kafka_batch_id_seq`, создаётся отдельно через `ingestion/01_sequence.sql`; проверить диапазон, занимаемый fixture и другими writers); он не должен попасть в выбранный диапазон. Не выбирать созданные coalesced batches повторно. Начать с 100–1000 событий, подобрать размер по нагрузке; `max_events` не более 10000. Очистка mapping запрещена, пока нужна трассировка или возможен replay.

`04_coalesce.sql` рассчитан на новую схему из `01_schema.sql` c новым статусом COALESCED. Для уже созданного batch_control существующее ограничение CHECK нужно отдельно обнаружить и безопасно обновить после анализа версии и состояния GP; этот пакет ничего не меняет автоматически. Нельзя просто применять `01_schema.sql` повторно к существующим схемам.

Пример, значения заменить на реальные из инвентаря, с psql `ON_ERROR_STOP=1` и без секрета в командной строке:

```sql
-- Sink и все writers уже остановлены и проверены. new_id зарезервирован.
SELECT oil_stg.coalesce_ready_batches(1001, 2000, 900001, 'kafka:oil.events.v1', 1000);
-- quality/02_coalesce_checks.sql с new_batch_id=900001: mismatch = 0.
SELECT oil_dds.apply_batch(900001);
SELECT batch_id,status FROM oil_stg.batch_control WHERE batch_id=900001; -- APPLIED
```

Количество READY может быть меньше диапазона, и выбор зависит от существующих batch; до вызова проверить точное множество и ожидаемый count. На полном объёме повторять последовательными непересекающимися диапазонами или выбирать их планировщиком. Эта версия не поддерживает параллельную обработку и ровно один coalesce на исходный batch. Не возвращать sink в работу, пока не восстановлены штатные условия fence. Если apply завершился ошибкой, coalesced batch остаётся READY, DDS rollback целиком, original batch остаётся COALESCED; исправить причину, повторить apply и не coalesce повторно. Ошибка самой coalesce откатывает всю её транзакцию. Предварительно проверить права на функции и ресурсы.

## История и первая цепочка

1. Запустить согласованный baseline генератора в Kafka только после готовности consumer; сохранить seed, версию, ожидаемые количества событий, payload unit и topic/partition offsets. Дождаться durable checkpoint по каждой партиции и убедиться, что event_log содержит соответствующие реальные записи, а ошибки/DLQ отсутствуют. Согласовать остановку producer и sink для проверяемого cut. Нельзя приравнять Kafka consumer commit к доказанному GP checkpoint без подтверждённого протокола sink.
2. Объединить READY batch по инструкции, вызвать `oil_dds.apply_batch` для каждого нового batch. Сверить `batch_coalesce_event_map` ↔ исходные Kafka позиции ↔ `event_log`; сравнить число уникальных event_id и версий, проверить `quality/01_checks.sql`. Полнота событий проверяется по manifest генератора и фактическим диапазонам Kafka, а не одной суммой строк.
3. После того как пришли все field и well, вызвать `SELECT oil_mart.refresh_production();`. Проверить `fact_well_day` по ключу `(well_hk,production_date)`, нули/отрицательные, соответствие статуса, число активных well-days, суммы тонн и `agg_field_day`; сверить вручную несколько скважин с исходными JSON. Записать counts, aggregates и cut; `v_field_production` — вход отчёта первой волны.
4. В отдельно согласованном наборе delta передать исправление версии, буквальный повтор и удаление, снова обеспечить доставку и обработку. Проверить историю `oil_dds.event` и спутников, отсутствие повтора event_id, корректное использование максимальной версии и удаление только актуальной версии. Конфликт того же event_id с другим JSON или одного entity_version с другим event_id должен откатывать batch. Негативные сценарии проводить только на отдельных тестовых ключах и не оставлять ошибочный batch в основном потоке.

## Вторая цепочка: простои

После успешного обновления добычи вызвать `SELECT oil_mart.refresh_downtime();`. Проверить `fact_downtime_interval`, `agg_field_downtime_day` и `v_field_performance`: длительность = `(end-start)` в часах, причина из справочника, скважина ACTIVE и имеется факт за UTC-день. Интервалы более суток или с пересечением по скважине должны отклоняться, не суммироваться дважды. Для нескольких well/day вручную сверить интервалы по исходным событиям и суммарное число часов. Пересчёты production и downtime — отдельные транзакции, поэтому для внешнего dashboard обеспечить окно остановки чтения либо отдельно разработать атомарный механизм release.

В результате сохранить отчёт: ID cut, partitions и checkpoint, версии кода, количества каждого события и объекта, количество ошибок по каждому gate, сведения о replay/update/delete, бизнес-агрегаты, кто и когда проверил. После проверки вернуть sink в исходное состояние в соответствии с планом. Никакие результаты не объявлять подтверждёнными до реального запуска и проверки.
