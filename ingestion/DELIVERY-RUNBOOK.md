# План загрузки нефтегазовой цепочки в Greenplum

Статус на 21 ноября 2026: baseline загружен, topic и GP connector созданы. Ниже сохранена исходная процедура, а не инструкция повторить загрузку; актуальное состояние — в `../docs/02-фактический-статус.md`. Вторую волну в DLH до вебинара не запускать. SQL исходной цепочки находится в `../gp/`.

## 1. Проверка и идентичности

1. Убедиться, что backup исходных GP и DLH объектов завершён и проверен, идентифицирована нужная GP БД, клонить или удалять ничего без соответствующей согласованной процедуры. Read-only сверить наличие схемы `oil_stg`, `event_log`, `batch_control` со статусом `COALESCED`, `kafka_checkpoint`, обеих таблиц coalesce mapping и функций применённых версий. Проверить, что отдельная последовательность `oil_stg.kafka_batch_id_seq` отсутствует, затем по необходимости создать её по `01_sequence.sql` после сверки с fixture и другими диапазонами batch_id. Старт 5000000000 — зарезервированное предложение, а не подтверждение глобальной уникальности; coalesce использует новый ID вне диапазона выбранных оригиналов и проверяет его отсутствие.
2. Выдать отдельную GP роль `oil_kafka_ingest`: только CONNECT к выбранной БД, USAGE на `oil_stg`, SELECT/UPDATE на `kafka_checkpoint`, INSERT на `event_log`, SELECT/INSERT/UPDATE на `batch_control`, USAGE на sequence. Секрет хранить в `/etc/kafka-demo/oil-gp-ingest-password`, владелец сервисной учётной записи, mode 0600; настройки `pg_hba.conf` — точечный hostssl для IP Kafka VM и новой роли; сертификат GP и имя хоста проверять через `verify-full`. Отдельно согласовать права исполнителя coalesce и apply; ingestion не получает этих расширенных прав.
3. В текущей Kafka брокер поддерживает mTLS, но topic ACL/authorizer не подтверждены. Отдельные сертификаты для oil producer и oil worker дают отдельные учётные данные, **сами по себе не ограничивают topic**. Для настоящего scoped доступа нужны авторизация брокера/ACL с запретом по умолчанию, отдельные разрешения на `oil.events.v1`, consumer group и internal/control topics; смену broker security выполнять отдельно с проверкой существующего commerce connector. Пока это не выполнено, нельзя утверждать изоляцию topics по сертификатам. Producer wrapper специально ссылается на ещё не созданные `/etc/kafka-demo/oil-producer-{ca.crt,crt,key}`; это не alias общего broker/node ключа.
4. Предпочтителен отдельный Connect worker и группа для oil с собственным mTLS identity и ограниченными внутренними топиками; REST только на loopback, без публичного порта. Оригинальный commerce worker/коннектор не заменять. Установить Oil connector как отдельный плагин с PostgreSQL JDBC в выделенном plugin directory; перезапуск только нового worker. `oil-gp-connector.template.json` содержит имя будущей роли и путь к будущему секрету, не создаёт ни то ни другое. Его `initial_state=PAUSED` и совместимость версии API проверить до регистрации.

## 2. Topic, checkpoints и запуск

1. Создать отдельный `oil.events.v1` с утверждёнными partition count, retention, RF и политикой безопасности; существующий single-broker стенд способен обеспечить лишь RF=1, это demo без HA. Для параллельности выбрать число partitions до публикации и не менять в течение опыта: порядок сохраняется только для одинакового key внутри одной партиции. Тема должна хранить историю на время baseline, migration и rollback; включать log compaction без отдельного пересмотра семантики пропусков нельзя.
2. До первого writer получить и сохранить вектор фактических earliest/high-next offsets. Для **нового и подтверждённо пустого** topic после проверки watermarks и partition count инициализировать `oil_stg.kafka_checkpoint` на фактических позициях каждой партиции; если topic уже содержит записи, выбрать и согласовать старт явно. Чужие или fixture offsets не использовать. Сохранить topic ID/cluster identity, период retention и hash манифеста.
3. Активировать только отдельный источник/GP sink после проверки backup/схемы, TLS и прав. Producer `oil_events.py` генерирует baseline только при явном `--phase baseline --kafka`; зафиксировать seed, fields, wells, days, версии образов/кода и checksum контракта. Доставить generator и необходимые библиотеки в отдельный каталог VM без автозапуска. Чтение секретов через защищённые файлы, только в runtime; никаких токенов в отчётах, репо, CLI или логах.
4. Sink обрабатывает одну запись одной GP-транзакцией: `event_log + batch_control OPEN→READY + kafka_checkpoint` в одном коммите, затем Connect commit. `source_name` строго `kafka:oil.events.v1`. После сбоя главный источник offset — GP `next_offset`, а не Kafka group commit; требуются ограничение одним активным task и внешнее fencing всех потенциальных writers. Рестарт при недоступном checkpoint, несовпадении или разрыве позиции должен останавливаться для разбора; допустимость Kafka offset gaps и процедура безопасного восстановления пока не автоматизированы.

## 3. Приём, coalesce, обработка и трасса

1. После отправки baseline остановить producer и убедиться, что delivery callbacks завершены без ошибок, никаких других producers нет. Считать vector брокера через `capture_offsets.py`: файл фиксирует только Kafka watermarks и не является GP snapshot. Убедиться, что `oil_stg.kafka_checkpoint.next_offset` для каждой партиции равен зафиксированному high-next, соответствующие события есть в staging, и не было потерь/ошибок. `offset lag=0` в Kafka group сам по себе недостаточен; не стирать или менять checkpoints.
2. Перед coalesce **приостановить sink и все apply/coalesce writers** и убедиться в полном отсутствии незавершённых транзакций; либо использовать проверенный внешний fence, который реально соблюдают все writers на весь период функции. `oil_stg.coalesce_ready_batches` сам никакой fence не выставляет. Отбирать только source `kafka:oil.events.v1`, статус READY и не более 10 000 реальных событий в одном вызове. Порядок batch_id не гарантирует порядок зависимостей между Kafka-партициями. В пределах freeze повторять группы до исчерпания нужных READY и дополнительно проверять, что вне выбранных интервалов не осталось относящихся к baseline batch.
3. На каждую группу атомарно создаётся новый READY batch, оригиналы становятся COALESCED, сохраняются `oil_stg.batch_coalesce_map` и `oil_stg.batch_coalesce_event_map`, а `event_log.batch_id` переходит к новому batch. `kafka_checkpoint` функция не меняет. После каждой группы сверить число оригиналов, число событий и mapping по каждой позиции `(topic,partition,offset)`, отсутствие пересечений/пропусков, source_name и неизменность offset vector. Ошибка или неоднозначность — rollback транзакции и разбор до повторного вызова; не удалять mapping ради повтора.
4. Применить готовые агрегированные batches `oil_dds.apply_batch` последовательно под тем же single-writer контролем. Затем проверить отсутствие FAILED/необработанных READY/неразрешённых зависимостей, ссылочную целостность и schema_version. Повтор replay по `event_id` должен совпадать байт-в-байт, а изменение того же `(event_type,entity_id,entity_version)` другим event_id должно останавливаться. Дождаться всех field/well и фактов/простоев до формирования двух витрин; глобальный порядок по разным keys/партициям Kafka не гарантирован.
5. Лишь после DQ и подтверждения общего GP snapshot сохранить контрольные количества и бизнес-агрегаты отдельно по каждой цепочке. Базовую миграционную границу фиксировать на согласованном срезе всех исходных объектов и векторе Kafka после producer freeze и остановки writers. Факт равенства watermark и checkpoint без freeze не доказывает согласованности GP. Любые прямые изменения GP вне журнала генератора не входят в этот event stream и требуют отдельного CDC либо запрета таких writes в пределах демонстрации.

Пример read-only инвентаризации партии после остановки writers (перед каждым решением о вызове coalesce):

```sql
SELECT b.batch_id, count(e.kafka_offset) AS event_count
FROM oil_stg.batch_control b
LEFT JOIN oil_stg.event_log e ON e.batch_id = b.batch_id
WHERE b.source_name = 'kafka:oil.events.v1' AND b.status = 'READY'
GROUP BY b.batch_id
ORDER BY b.batch_id
LIMIT 10000;

SELECT topic, kafka_partition, next_offset
FROM oil_stg.kafka_checkpoint
WHERE topic = 'oil.events.v1'
ORDER BY kafka_partition;
```

По результату оператор выбирает диапазон только после проверки суммарного `event_count ≤ 10000` и зафиксированного fence; `p_new_batch` получает из зарезервированного sequence, проверяя отсутствие пересечения и конфликтов. Затем вручную вызывает `oil_stg.coalesce_ready_batches(first_id, last_id, new_id, 'kafka:oil.events.v1', 10000)` в управляемой транзакции. Пример намеренно не подставляет выдуманные ID и не запускает функцию автоматически. Если в диапазон попали записи другого source или не READY, функция их пропускает; после каждого вызова сверяется полный состав выбранного baseline, а не только числовые границы batch.

## 4. Нагрузка и наблюдаемость

Для стандартных `--fields 5 --wells 40 --days 365` подготовленный генератор при расчёте в памяти выдаёт **15 525 событий**: 5 field, 40 well, 14 600 production_day и 880 downtime; суммарно около 5 126 948 байт JSON (≈4,89 MiB), без keys, Kafka protocol, индексов, replication и служебных данных. Delta — 5 сообщений, 4 уникальных event_id, одно повторное сообщение. Это объём synthetic payload, не обещание производительности.

В текущем sink это **15 525 GP транзакций и 15 525 исходных batch** до coalesce. На скоростях 10/50/100 сообщений в секунду нижняя оценка только приёма — соответственно около 25,9/5,2/2,6 минуты, без старта, накладных расходов, обработки, coalesce и DQ; реальные цифры не измерены. Предел функции 10 000 событий означает минимум 2 coalesce вызова при полном baseline, но реальные интервалы и число вызовов определяются фактическими batch IDs и проверками. При DQ/целостности сложность SQL и конкуренция с GP требуют отдельного нагрузочного профиля; не выдавать оценку за SLA.

На демо выводить на временной шкале: producer отправлено/ошибки/pending, Kafka partition low/high-next и consumer lag, GP checkpoint по partition, количество batch OPEN/READY/COALESCED/APPLIED/FAILED, задержку самого старого READY, счётчики mapping, reject и ошибок DQ, время coalesce/apply и свежесть каждой витрины. Отдельно фиксировать restart и причину остановки, владельца, run ID, offset manifest и snapshot границу. Алерты и сбор метрик как эксплуатируемые сервисы пока не развернуты; heartbeat `RUNNING` не доказывает успешный приём.
