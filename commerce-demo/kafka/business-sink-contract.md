# Проект контракта бизнесового Iceberg sink

Это незапущенный и не зарегистрированный шаблон `iceberg-business-sink.template.json`. `EnvelopeToStaging` из `smt-src` прошёл изолированный sink-тест на временном topic и таблице с четырьмя синтетическими сообщениями; временный JAR после теста удалён. Проверка подтвердила сохранение metadata и envelope в staging, но не обработку dedup, upsert, delete или существующей бизнесовой таблицы. Не снимать PAUSED и не называть конфигурацию production-ready до реализации остальных шагов.

`StringConverter` передаёт исходный JSON как строку; SMT получает `SinkRecord` с метаданными Kafka и строит Struct `topic`, `kafka_partition`, `kafka_offset`, `batch_id`, `received_at`, `event_json`, соответствующий именам планового `dlh.commerce_stg.kafka_event`. По умолчанию разрешён только `commerce.events.v1`; `allowed.topic` позволяет задать другой единственный topic для изолированной проверки. Принимаются партиции 0–127, offsets 0–2^56−1, корректный JSON object с обязательными полями envelope и операцией U/D; Kafka tombstone отклоняется. `event_json` сохраняет исходный текст. Полная бизнес-валидация выполняется ниже по цепочке.

`batch_id=(partition << 56) | offset` задаёт детерминированный ID *одной Kafka записи в рамках фиксированного топика*. Это не ID пакета Greenplum, который выдаёт собственная последовательность, и не доказательство 1:1 между batch_id двух контуров. `received_at` остаётся NULL: Kafka timestamp нельзя автоматически считать временем приёма в Lakehouse; при необходимости Airflow/обработка должны задать явное время после коммита. Тест на автоматически созданной технической таблице подтвердил отображение типов, включая nullable `TIMESTAMP WITH TIME ZONE`; совместимость с заранее созданной целевой таблицей остаётся проверить.

SMT не создаёт `commerce_stg.batch_control` и не делает атомарную транзакцию двух Iceberg-таблиц. Перед реальным запуском требуется согласовать оркестратор: после подтверждённого Iceberg snapshot фиксировать в отдельном журнале manifest границ topic/partition/offset и состояние batch, обеспечивать идемпотентность и восстановление после сбоя между snapshot и журналом. Сверять две стороны по (topic, partition, offset), event_id, содержимому и согласованной границе, а не по batch_id. Kafka Connect и Iceberg сами по себе не обеспечивают уникальность строк по этим ключам; нужны отдельные проверки дубликатов и политика повторов/коррекций.

Для запуска также нужны зарегистрированные и подготовленные целевые таблицы и scoped grants, отдельный worker с CA truststore, созданный control topic, проверка стабильной схемы и тесты поздних событий, replay, delete, рестартов, потери связи и обработки отставания. Выбор границы и стартовые offsets необходимо фиксировать отдельно: наличие параметра `initial_state=PAUSED` в примере не создаёт моментальный снимок Greenplum и не гарантирует отсутствие пропусков. Источник `commerce.events.v1` — журнал синтетических событий, не CDC произвольных изменений в Greenplum.
