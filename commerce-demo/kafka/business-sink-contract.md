# Проект контракта бизнесового Iceberg sink

Это незапущенный и не зарегистрированный шаблон `iceberg-business-sink.template.json`. `EnvelopeToStaging` из `smt-src` скомпилирован против установленных Kafka Connect API, но не установлен и не проверен в изолированном sink. Проверка выше на технической таблице не проверяла этот SMT, бизнес-envelope, целевую схему и обработку изменений. Не снимать PAUSED и не называть конфигурацию production-ready до отдельного прогона.

`StringConverter` передаёт исходный JSON как строку; SMT получает `SinkRecord` с метаданными Kafka и строит Struct `topic`, `kafka_partition`, `kafka_offset`, `batch_id`, `received_at`, `event_json`, соответствующий именам планового `dlh.commerce_stg.kafka_event`. Он принимает только `commerce.events.v1`, партиции 0–127, offsets 0–2^56−1, корректный JSON object с обязательными полями envelope и явно заданную операцию U/D; Kafka tombstone отклоняется. `event_json` сохраняет исходный текст, а не сериализацию преобразованного объекта. Полная бизнес-валидация должна выполняться ниже по цепочке.

`batch_id=(partition << 56) | offset` задаёт детерминированный ID *одной Kafka записи в рамках фиксированного топика*. Это не ID пакета Greenplum, который выдаёт собственная последовательность, и не доказательство 1:1 между batch_id двух контуров. `received_at` остаётся NULL: Kafka timestamp нельзя автоматически считать временем приёма в Lakehouse; при необходимости Airflow/обработка должны задать явное время после коммита. Возможность корректной записи nullable logical timestamp в тип `TIMESTAMP WITH TIME ZONE` и отображение всех остальных типов конкретной версией коннектора ещё требуют проверки.

SMT не создаёт `commerce_stg.batch_control` и не делает атомарную транзакцию двух Iceberg-таблиц. Перед реальным запуском требуется согласовать оркестратор: после подтверждённого Iceberg snapshot фиксировать в отдельном журнале manifest границ topic/partition/offset и состояние batch, обеспечивать идемпотентность и восстановление после сбоя между snapshot и журналом. Сверять две стороны по (topic, partition, offset), event_id, содержимому и согласованной границе, а не по batch_id. Kafka Connect и Iceberg сами по себе не обеспечивают уникальность строк по этим ключам; нужны отдельные проверки дубликатов и политика повторов/коррекций.

Для запуска также нужны зарегистрированные и подготовленные целевые таблицы и scoped grants, отдельный worker с CA truststore, созданный control topic, проверка стабильной схемы и тесты поздних событий, replay, delete, рестартов, потери связи и обработки отставания. Выбор границы и стартовые offsets необходимо фиксировать отдельно: наличие параметра `initial_state=PAUSED` в примере не создаёт моментальный снимок Greenplum и не гарантирует отсутствие пропусков. Источник `commerce.events.v1` — журнал синтетических событий, не CDC произвольных изменений в Greenplum.
