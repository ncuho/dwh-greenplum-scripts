# Iceberg Sink: подготовка без запуска

На worker установлен обнаруживаемый Apache Iceberg Sink 1.9.2; экземпляр коннектора не зарегистрирован. Бизнес-таблицы и control topic им не создавались. Чтение журнала и запись в Iceberg не запускались.

Источник параметров и поведения — [документация Iceberg 1.9.2](https://iceberg.apache.org/docs/1.9.2/kafka-connect/): `iceberg.catalog.type=rest`, `iceberg.catalog.uri`, `iceberg.catalog.warehouse`, а для JSON требуются корректный `JsonConverter` и сопоставление структуры событий со схемой целевой таблицы. Наш envelope содержит вложенный `payload` и операции U/D: маршрутизацию по типу, обработку удалений, повторов и порядка нужно проектировать и проверять отдельно. Подставлять GP Sink конфигурацию или объявлять обновления строк рабочими нельзя.

Требуется назначить отдельную machine identity CIAM с `client_credentials`, scope и audience только LakeKeeper, совместимую с его OIDC, а затем выдать нужные минимальные права на конкретные таблицы/namespace и scoped права хранения; создать отдельный секрет с ограниченным доступом. Наличие Hydra public/admin API и LakeKeeper deployment проверено read-only в Kubernetes. Kubernetes RBAC на создание jobs/secrets не доказывает полномочий на регистрацию CIAM клиента или назначение LakeKeeper/S3 разрешений. Предыдущий анализ штатного hook и формата namespace assignments: `vk-data-migration-2026-11-15/runbooks/spark-demo/credential-provisioning-plan.md`. Не копировать существующий общий секрет Cedrus, не предоставлять административные и warehouse-wide права.

Для постоянной конфигурации нужен проверенный безопасный provider секретов и подтверждённый механизм штатного обновления OAuth credentials: статический короткоживущий bearer в `connect-gp.json`, Git или логе неприемлем. До реальной регистрации определить целевые FQN, модель состояний, схему Kafka Connect и control topic с подходящей политикой репликации. Протестировать отдельный технический namespace с mock/тестовыми данными, ротацию, перезапуск и контрольный диапазон offsets. Совместимость LakeKeeper REST, remote signing или scoped S3 credentials и Kafka Connect плагина пока не доказана.

Сеть подключена: отдельный интерфейс и split DNS дают Kafka VM частную связность с CIAM и LakeKeeper, Java HTTPS проверен с отдельным truststore. Identity, права и token refresh остаются неподтверждёнными. Актуальная конфигурация и ограничения — в разделе «Фактическое частное подключение» файла README.md.
