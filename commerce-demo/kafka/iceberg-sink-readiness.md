# Iceberg Sink: подготовка без запуска

На worker установлен обнаруживаемый Apache Iceberg Sink 1.9.2; экземпляр коннектора не зарегистрирован. Бизнес-таблицы и control topic им не создавались. Чтение журнала и запись в Iceberg не запускались.

Источник параметров и поведения — [документация Iceberg 1.9.2](https://iceberg.apache.org/docs/1.9.2/kafka-connect/): `iceberg.catalog.type=rest`, `iceberg.catalog.uri`, `iceberg.catalog.warehouse`, а для JSON требуются корректный `JsonConverter` и сопоставление структуры событий со схемой целевой таблицы. Наш envelope содержит вложенный `payload` и операции U/D: маршрутизацию по типу, обработку удалений, повторов и порядка нужно проектировать и проверять отдельно. Подставлять GP Sink конфигурацию или объявлять обновления строк рабочими нельзя.

Требуется назначить отдельную machine identity CIAM с `client_credentials`, scope и audience только LakeKeeper, совместимую с его OIDC, а затем выдать нужные минимальные права на конкретные таблицы/namespace и scoped права хранения; создать отдельный секрет с ограниченным доступом. Наличие Hydra public/admin API и LakeKeeper deployment проверено read-only в Kubernetes. Kubernetes RBAC на создание jobs/secrets не доказывает полномочий на регистрацию CIAM клиента или назначение LakeKeeper/S3 разрешений. Предыдущий анализ штатного hook и формата namespace assignments: `vk-data-migration-2026-11-15/runbooks/spark-demo/credential-provisioning-plan.md`. Не копировать существующий общий секрет Cedrus, не предоставлять административные и warehouse-wide права.

Для постоянной конфигурации нужен проверенный безопасный provider секретов и подтверждённый механизм штатного обновления OAuth credentials: статический короткоживущий bearer в `connect-gp.json`, Git или логе неприемлем. До реальной регистрации определить целевые FQN, модель состояний, схему Kafka Connect и control topic с подходящей политикой репликации. Протестировать отдельный технический namespace с mock/тестовыми данными, ротацию, перезапуск и контрольный диапазон offsets. Совместимость LakeKeeper REST, remote signing или scoped S3 credentials и Kafka Connect плагина пока не доказана.

Сеть подключена: отдельный интерфейс и split DNS дают Kafka VM частную связность с CIAM и LakeKeeper, Java HTTPS проверен с отдельным truststore. Identity, права и token refresh остаются неподтверждёнными. Актуальная конфигурация и ограничения — в разделе «Фактическое частное подключение» файла README.md.

## Фактическая проверка CIAM и обновления токенов

Создан отдельный client `webinar-iceberg-b33bfcb7f5db`, principal LakeKeeper `oidc~webinar-iceberg-b33bfcb7f5db`, tenant `4aaf3f29-90bd-5731-a98d-b30a63aeabce`; секрет выдан заново и хранится только в `/etc/kafka-demo/iceberg-client-credential` на Kafka VM с правами 0600. Client `client_secret_post` выполняет `client_credentials` с LakeKeeper scope/audience; токен и whoami проверены. Права на данные ему не выдавались. Временные клиенты и LakeKeeper users в тестах удалены через штатные API, DELETE 204 и GET client 404.

Штатный Iceberg OAuth2Manager 1.9.2 получает первоначальный токен, но с коротким 20-секундным TTL не переиздал его за 25 секунд; token-exchange на CIAM вернул 400 `invalid_request`. Текущий способ авторизации `client_secret_post` необходим, поскольку Iceberg отправляет credential в форме, а `client_secret_basic` отклонил такую форму (401). Ручное получение нового client_credentials token с истекшим предыдущим проверено, но это не автоматический refresh штатного OAuth2Manager.

Разработан пользовательский, не входящий в Apache Iceberg `demo.iceberg.CiamAuthManager`: при очередном обращении к каталогу переиздаёт token через client_credentials до истечения TTL, считывая секрет из указанного файла; разрешён только заранее известный HTTPS CIAM и LakeKeeper IP, файл проверяется на отсутствие прав group/others, ошибки закрывают доступ. Java harness с реальным CIAM и временным 20-секундным клиентом подтвердил, что при повторном запросе после TTL токен изменился; запрос к постороннему хосту отклонён. Временный тестовый клиент удалён. Это обновление по обращению к каталогу, а не фоновой refresh, и не проверка рабочего sink под нагрузкой.

JAR `/opt/kafka-demo/plugins/iceberg/webinar-ciam-auth-1.jar` (SHA-256 `890211b340755040f66bad00fdce60f20d62d7999eb93f5b6d09f1d1c4466219`) находится в том же classloader-каталоге, что и Iceberg plugin; source `/opt/kafka-demo/iceberg-auth-source/CiamAuthManager.java`. Предполагаемые свойства connector: `iceberg.catalog.rest.auth.type=demo.iceberg.CiamAuthManager`, `iceberg.catalog.ciam.credential-file=/etc/kafka-demo/iceberg-client-credential`. Их следует использовать только после проверки полного sink и независимого worker truststore; они пока не применены. После установки JAR worker перезапущен, GP connector и его task `RUNNING`, экземпляр Iceberg sink не создан.

Прямой запрос новой identity к `/catalog/v1/config?warehouse=dlh` вернул 403 `ProjectActionForbidden`; исходный код LakeKeeper 0.11.2 подтверждает, что нужны project action `ListWarehouses`, затем warehouse action `GetConfig` ещё до namespace permissions. Для изолированного sink нужны подтверждённый авторизованный management issuer, минимальные project/warehouse permissions и временный namespace с ограниченными правами и storage scope; способ безопасно предоставить их пока не подтверждён. S3 remote-signing/права записи и end-to-end sink не проверены. Production namespace и финальная миграция не затрагивались.

Отдельный тестовый Connect worker, topic и connector отправили одну запись `probe_id=webinar-connect-test-1`, `value=42` в созданную только для теста таблицу `dlh.kafka_smoke_20261120_da2dadb8.sink_probe`. LakeKeeper подтвердил append snapshot с `added-records=1`, `total-records=1`, `total-data-files=1` и Kafka commit ID. Независимая программа Iceberg Java прочитала через S3 с включённой проверкой TLS: `PROBE_READ_COUNT=1`, `PROBE_VALUE_MATCH=true`. Для чтения в её временный classpath потребовался `hadoop-mapreduce-client-core:3.4.1`; это дополнение для readback harness, не изменение worker. В первые циклы коннектор сообщал `commit timeout / 0 tables`, но позднее snapshot с данными появился; причина задержки не установлена.

Test connector удалён, worker остановлен и удалён, его 3 internal topics и 2 тестовых Kafka topics удалены; исходный GP connector и task после этого `RUNNING`. LakeKeeper table удалена с purge и namespace удалён (404), scoped grants удалены; effective project/warehouse actions identity после обновления авторизатора пусты. S3 ListObjectsV2 по тестовому prefix `data/01a1f8d6-c033-7f20-9580-aa8caa4d976b/` вернул 0 объектов и `IsTruncated=false`. Проба не доказывает работоспособность бизнес-envelope SMT или перенос инкрементов и не является финальной миграцией.
