Статус: Kafka и Connect развёрнуты; GP sink проверен на отдельном тестовом топике. Генератор и финальная миграция не запускались. Актуальные сведения находятся в разделе «Фактическое развёртывание».

## Размещение и доступ

Выделить отдельную VM в VK Cloud в проекте Greenplum `a784cccc62434c279df4ecc1258b2674`, после проверки актуального проекта, сети, квот, тарифов и связности. Для однокомпонентного демонстрационного стенда ориентир — 4 vCPU, 8–16 ГиБ RAM, 80–100 ГиБ диска; sizing уточнить по нагрузке. Это не высокодоступная конфигурация. Не размещать Kafka на координаторе или сегментах Greenplum.

Запустить Kafka в режиме KRaft и Kafka Connect на приватной сети, выделить отдельную системную учётную запись и диски, включить TLS и авторизацию, ограничить security groups конкретными адресами клиентов. Не открывать брокер и Connect REST публично; предоставить доступ администратору через защищённый контур. Секреты и сертификаты хранить в защищённом хранилище, не в Git или образе. Отдельно проверить DNS, advertise listeners и маршруты до GP, LakeKeeper и S3.

Подготовить топик `commerce.events.v1` с заранее выбранными числом партиций, retention и ACL. Ключ сообщения `event_type:entity_id` обеспечивает порядок для ключа внутри одной партиции при неизменной схеме распределения; глобального порядка нет. Для Connect предусмотреть отдельные внутренние топики конфигураций, offsets и статусов, мониторинг consumer lag, ошибок, DLQ и перезапусков. Один брокер не обеспечивает отказоустойчивость: для production нужен отдельно спроектированный кластер и репликация.

## Подключение цепочек

1. Greenplum 6.26.2: проверить совместимость драйвера и конкретного sink-коннектора с установленной версией GP. Не полагаться на PostgreSQL `ON CONFLICT`: insert-only landing и обработка повторов и корректировок должны быть реализованы и проверены в GP. Вложенный `payload` необходимо явно преобразовать в поддерживаемую коннектором схему или сериализованное поле; готовность стандартного JDBC Sink не подтверждена.
2. Iceberg: выбрать и установить совместимую версию Kafka Connect Iceberg Sink и необходимые плагины. Проверить REST API LakeKeeper, авторизацию, доступ к S3, схему и обработку схемных изменений. Применение исправлений и удалений зависит от подтверждённых возможностей выбранного коннектора и конфигурации; до проверки считать это нерешённым.
3. Синхронизация: зафиксировать offsets отдельно по каждой партиции, воспроизводимую границу состояния GP и процедуру сверки; доказать связь среза с позициями журнала. События после границы сохранять до запуска потребителя, затем повторно обрабатывать с идемпотентностью по `event_id` и версии сущности. Журнал событий генератора — не CDC из WAL Greenplum; прямые изменения в GP он не захватит. Exactly-once всей цепочки и атомарность нескольких таблиц не предполагаются.
4. До демонстрации проверить изоляцию учётных записей, DLQ, повторное чтение, коррекции и удаления, запоздавшие события, отставание, согласованность метрик и возврат на исходную цепочку. Ни один из пунктов пока не подтверждён фактическим прогоном.

## Генератор

`commerce_events.py` поддерживает базовую фазу и последующую delta: исправление отгрузки, удаление возврата, запоздавшую версию товара и точный повтор события. JSON envelope содержит `event_id`, `event_type`, `entity_id`, `entity_version`, `op`, `event_time` и `payload`. Суммы представлены десятичными строками; бизнес-смысл версий и время действия необходимо согласовать с моделью приёмника.

Генератор по умолчанию ничего не публикует: CLI требует `--phase` и один явный режим `--output` или `--kafka`. Для Kafka обязательны `COMMERCE_KAFKA_BOOTSTRAP` и `COMMERCE_KAFKA_SECURITY_PROTOCOL=SSL|SASL_SSL`; для SASL также механизм, имя и пароль через переменные окружения. `--output` создаёт только новый файл и не перезаписывает существующий. Для Python API сначала вычислить `scenario_seed(seed, products, stores, shipments)` и передать результат в `baseline` или `delta` с теми же параметрами: это обеспечивает совпадение с CLI. Фазы обязаны использовать одинаковые параметры.

Наличие idempotent producer и `acks=all` не гарантирует end-to-end exactly-once. Публикация выполняется только по отдельному операционному решению; автозапуск генератора не настраивать.

## Исходный consumer Kafka → Greenplum

Подготовлены `gp_consumer.py` и дополнительный DDL `gp_consumer_schema.sql` для согласованных `demo_stg.kafka_event` и `demo_stg.batch_control`. Это исходный код, не развёрнутый и не проверенный в реальном окружении. Перед установкой проверить поддержку `SEQUENCE`, `LOCK TABLE`, транзакций и SQL-драйвера именно в используемом GP 6, а также права сервисной учётной записи. Отдельная таблица checkpoint и staging должны быть размещены в той же транзакционной базе GP. Диапазон идентификаторов последовательности должен быть заранее зарезервирован и не пересекаться с fixture и прочими загрузчиками.

Consumer назначает партиции вручную и не вступает в group rebalance: список партиций задаётся явно. Текущая версия рассчитана строго на **один активный процесс на все назначенные партиции**, в том числе во время перезапуска; необходим внешний надёжный механизм fencing. Локальная блокировка таблицы сериализует транзакции, но не заменяет fencing нескольких процессов или управления ownership при смене узла. Автоматическое масштабирование, смена набора партиций, rebalance и автоматический failover не поддержаны. Оператор контролирует ownership и перезапускает consumer только после остановки прежнего процесса.

Для каждой записи в единой транзакции создаются batch `OPEN`, staging-событие, статус `READY` и новый `next_offset` в GP. После коммита GP синхронно коммитится позиция Kafka; при сбое Kafka commit процесс завершается, а при перезапуске позиция берётся из GP, а не Kafka. Обработка ODS/Vault и `APPLIED` принадлежат отдельному оркестратору с соблюдением единственного writer; consumer её не запускает. Базовый consumer создаёт один batch на событие, поэтому подходит для демонстрационной нагрузки, но требует пакетной реализации и нагрузочных испытаний для production.

Checkpoint нужно явно инициализировать для каждой партиции на согласованной позиции после проверки low/high watermark; `fixture.baseline` и его вымышленные offsets не являются позициями Kafka. На старте сверяется попадание checkpoint в доступный диапазон. Consumer намеренно останавливается при любом разрыве offsets, повреждённом JSON, tombstone или ошибке обработки, не сдвигая checkpoint: пробелы могут быть штатными из-за транзакционных записей и compaction, поэтому такой режим не является универсальным production-потребителем. Для полноценной эксплуатации нужна проверенная политика обнаружения допустимых пропусков и DLQ без потери данных. Консьюмер проверяет только структуру envelope; полная бизнес-валидация происходит downstream и ошибочный `READY` batch блокирует применение до исправления.

Параметры: явные `--topic`, `--partitions`, `--max-messages`, опционально `--idle-timeout`; брокер, group ID и TLS/SASL через `COMMERCE_KAFKA_*`. GP использует libpq `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGSSLROOTCERT`, `PGPASSFILE`, принудительно `sslmode=verify-full`; пароль не передаётся в аргументах. Сертификаты, парольный файл и права к ним необходимо настроить средствами платформы. Коммит Kafka — дополнительная наблюдаемость, не общий атомарный коммит Kafka и GP. Exactly-once для всей бизнес-цепочки не заявляется.

### Read-only инвентаризация связности до подключения интерфейса

В видимом VK Cloud проекте Kafka/GP находится в сети `gp-migration-demo-network` (`10.77.25.0/24`) и маршрутизаторе `gp-migration-demo-router`; сеть с именем `dp-xcpwfgn5-network` имеет диапазон `10.101.0.0/24` и другой роутер. В отдельной сети `ArenadataDB8095-main` использован тот же `10.101.0.0/24`: при объединении доменов маршрутизации возникает конфликт адресов, поэтому нельзя считать обе сети одновременно достижимыми по одному префиксу. Явных статических маршрутов у видимых роутеров нет; видимых VPN services и network RBAC sharing нет. Результат относится только к доступному облачному проекту и правам текущей учётной записи.

У сети с именем DP есть Octavia порт `10.101.0.251`, но его принадлежность интересующим LakeKeeper/CIAM и доступность приложений не установлены. Адрес LakeKeeper `10.0.2.16` среди доступных Neutron ports не найден. Локальный kubectl-контекст имел timeout к API `10.139.114.10:6443`, поэтому определить размещение VIP и проверить сетевые политики Kubernetes из этого контекста не удалось.

Вариант с дополнительным приватным интерфейсом Kafka VM в нужной подтверждённой сети не потребовал бы изменения таблиц маршрутов других машин, но сейчас не доказано, что найденная сеть DP является сетью целевой платформы и что из неё доступны утверждённые private endpoints LakeKeeper и CIAM. Кроме того, необходимо проверить guest routing, обратный путь, SG/NetworkPolicy, DNS, TLS и не пересечься с `10.101.0.0/24` Arenadata. Альтернатива при размещении контуров в разных сетевых доменах — согласованное частное подключение Direct Connect или VPN с непересекающимися адресами и узкими маршрутами; применимость и поддержка в конкретной платформе нуждаются в проверке владельцами сети. [VK Cloud: Direct Connect](https://land.vkcloud-static.ru/direct-connect/). Никаких маршрутов, VPN, сетевых интерфейсов или публичных прокси в ходе этой проверки не создавалось.

Текущая cloud-сессия видит в `/auth/projects` только GP-проект и не позволяет инвентаризировать права, маршруты и сети проекта платформы.

Более точная постановка для платформенных сетевых администраторов: обеспечить частный двусторонний путь `10.77.25.20 → 10.0.2.16:443, 10.0.2.242:443` и обратный маршрут, затем DNS `dp-103.mcs.local → 10.0.2.242`, сертификаты, правила периметра и доступ отдельной service identity. Подтвердить доступный для этих проектов механизм межпроектного/межзонального подключения; проверить реальные CIDR, возможные пересечения и владельцев маршрутов. Прямое прикрепление второго сетевого интерфейса потребовало бы подтверждённого разрешённого совместного использования целевой сети между проектами и не доказано поддерживаемым здесь. Публичный прокси не предлагается. Для авторизованного Kafka→Iceberg затем необходимы проверенные CIAM token lifecycle и LakeKeeper/S3 права.

### План общей сети Sprut до подключения интерфейса

Подтверждённая пользователем сеть Data Platform: `dp-103`, network ID `08fdaa72-d775-45c6-9a8e-44a98d713089`, subnet ID `27c60550-99bb-49c3-9af5-52e134dc51ac`, `10.0.2.0/24`. По ранее прочитанным атрибутам GP сеть тоже использует SDN Sprut. С платформенной установочной VM прямой TCP до `10.77.25.20:9093` и `10.77.25.10:5432` заканчивается тайм-аутом; `ip route get` показывает только default gateway, наличие действующего частного пути или VPN не подтверждено. Из сети платформы оба kube-vip `10.0.2.16:443` и `10.0.2.242:443` доступны по TCP.

В VK Cloud есть [штатный механизм общих сетей](https://github.com/vk-cs/docs-public/blob/master/docs/ru/networks/vnet/instructions/shared-nets/shared-nets.md) между проектами в пределах одной SDN; для Sprut он доступен по умолчанию. Кандидат на решение без изменения маршрутов остальных устройств: владелец DP открывает в облачном UI сеть `dp-103` → «Поделиться сетью» → «Другие проекты» → OpenStack project ID `a784cccc62434c279df4ecc1258b2674`, пользователь GP проекта принимает приглашение, затем администратор подключает отдельный порт общей сети только к Kafka VM. Это ещё не выполнено. До выполнения нужно проверить, что оба проекта находятся в одной доступной SDN/регионе, сеть действительно доступна в AZ VM `MS1`, IP свободен, kube-vip и SG/NetworkPolicy разрешают новый источник, и второй интерфейс не поменяет default route, DNS и SSH-маршрут VM. Не превращать Kafka VM в межсетевой маршрутизатор, запретить IP forwarding и ограничить входящие и исходящие направления. Платформе принадлежит решение о предоставлении сети; если механизм неприменим, нужен согласованный приватный сетевой канал.

DNS проверен на DP bastion: `/etc/resolv.conf` использует `10.0.2.3`; `dig @10.0.2.3 dp-103.mcs.local A` возвращает `10.0.2.242`. Подтверждённый пользователем `10.0.2.254` по UDP возвращает для этого имени NXDOMAIN. Поэтому для Kafka VM потребуется согласованный split DNS/forwarder к рабочему resolver либо поддерживаемая запись; менять глобальный DNS без проверки нельзя.

Команды только для просмотра после получения действующих, отдельно scoped cloud credentials в каждом проекте: `openstack network show 08fdaa72-d775-45c6-9a8e-44a98d713089`, `openstack subnet show 27c60550-99bb-49c3-9af5-52e134dc51ac`, `openstack network rbac list`, `openstack port list --network 08fdaa72-d775-45c6-9a8e-44a98d713089`, `openstack server show 04892b1a-b994-4814-85a8-0ad69a03fad3`. Доступы: просмотр сети и RBAC в DP project, просмотр и присоединение интерфейса VM в GP project; право делиться сетью и принимать приглашение согласно облачной документации. Параметры и формат RBAC/доступности AZ дополнительно проверить в UI/API, не предполагать автоматическое принятие. Эти команды не создают ресурсов и не выводят учётные данные.
