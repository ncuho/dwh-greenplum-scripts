# Карта объектов и реальных зависимостей в проектном SQL

Эта карта построена по файлам пакета, а не по живому каталогу. Создание, исполнение, регистрации Superset и lineage в Data Catalog должны проверяться отдельно. Стрелки ниже означают использование в коде, а не подтверждённые связи в платформе.

| Слой | Объект | Зерно и назначение | Непосредственные зависимости |
|---|---|---|---|
| STG | `demo_stg.kafka_event` | позиция topic/partition/offset и JSON события | фактический Kafka consumer не реализован; fixture — локальный synthetic источник |
| STG | `demo_stg.batch_control` | одна запись на batch, состояние и манифест | оркестратор/fixture |
| STG | `demo_stg.v_event_parsed` | разобранный конверт события | `kafka_event` |
| ODS | `demo_ods.event` | уникальный event_id; исходный документ и версия сущности | `v_event_parsed`, `batch_control`, функция `demo_ods.apply_batch` |
| Vault | `hub_product`, `hub_store`, `hub_shipment`, `hub_return` | один бизнес-ключ продукта, магазина, отгрузки, возврата | `event` соответствующего типа |
| Vault | `link_shipment` | связь отгрузки с продуктом и магазином | `event` типа shipment |
| Vault | `link_return` | связь возврата и отгрузки | `event` типа return |
| Vault | `sat_product`, `sat_store` | версия атрибутов измерения по событию | `event` соответствующего типа |
| Vault | `sat_shipment`, `sat_return` | версия факта по событию; op и связь | `event` соответствующего типа |
| Vault | `v_shipment_current`, `v_return_current` | текущая неделетированная версия по максимальному entity_version | одноимённый satellite |
| DM | `dim_product`, `dim_store` | версия измерения и временной интервал | соответствующий satellite; `demo_dm.rebuild` |
| DM | `fact_shipment` | текущая отгрузка | `v_shipment_current`, `hub_shipment`, `link_shipment`, оба dim |
| DM | `fact_return` | текущий возврат | `v_return_current`, `hub_return`, `link_return`, `fact_shipment` |
| DM | `sales_day` | дата возврата/отгрузки × регион × категория × валюта | оба факта и оба измерения; агрегации отдельно |
| DM | `v_sales_dashboard` | представление витрины для BI | `sales_day` |

Полные имена Vault и DM имеют префиксы `demo_vault.` и `demo_dm.` соответственно. В `demo_ods.apply_batch` все Vault-таблицы заполняются из ODS напрямую, а не через FK к hubs; это намеренное упрощение, поэтому доступность связанных hub-ключей и collision guard надо проверять отдельно. `demo_dm.rebuild` полностью пересчитывает DM в одной транзакции GP; при ошибке транзакция откатывается. Для корректности требуется ограничение на единственного писателя.

## Бизнес-смысл

Отгрузка приносит `quantity × unit_price`, возврат вычитает собственные `quantity × unit_price` в день возврата; `net_amount = shipment_amount - return_amount`. Возврат связывается с версией продукта и магазина на дату родительской отгрузки. Это оборот, не прибыль и не выручка по признанию доходов; стоимость товаров, налоги, скидки и поступление платежей здесь не моделируются. При нескольких возвратах их количество не должно превышать отгруженное; валюта и дата проверяются по родительской отгрузке. Если бизнесу требуется первоначальная цена или стоимость по партии, контракт и проверки необходимо расширить.

## Целевой расчёт из кода

`dlh/sales_job.py` читает только `dlh.commerce_vault.sat_product`, `sat_store`, `sat_shipment`, `sat_return`, `hub_shipment`, `hub_return`, `link_shipment`, `link_return`, строит временные представления измерений, фактов и агрегата и выводит их количество и ограниченные примеры. При явном `--publish` пишет только `dlh.commerce_dm.sales_day`; таблицы `dim_*` и `fact_*` в этой реализации не публикуются. Следовательно, эта заготовка не является переносом всей цепочки 1:1, и создавать lineage в каталог для отсутствующих целевых шагов нельзя. До выпуска нужны механизм согласованного набора input snapshots, fencing и полные вычисления с целевыми деталями и проверкой эквивалентности; реализации CDC здесь нет.

## Результат ревью и открытые ограничения

* Replay идентичного события допускается, конфликт версии или документа отклоняется. Сравнение документа побайтное: producer должен использовать стабильную сериализацию JSON.
* SQL работает с единым writer; не зафиксирован источник истинных Kafka positions в транзакции GP. Синтетические номера fixture — локальные последовательные номера, не Kafka offsets.
* `SELECT DISTINCT` при создании hub/link учитывает `record_source`; одинаковый бизнес-ключ из разных источников в одном batch способен породить дубли. До multi-source ingestion нужно исправить группировку и добавить gate на коллизии/уникальность. Для одной Kafka-темы и одного fixture в отдельном batch этот конкретный случай не возникает.
* Проверки коллизий в `greenplum_checks.sql` покрывают только product/store, не все hubs/links; hash MD5 не является гарантией отсутствия коллизий.
* Нет реализованного регулярного ingestion, массового CDC, автоматического управления ролями, DAG, зарегистрированного dashboard и реального lineage. Наличие исходных файлов не доказывает их работу.
* Партиционирование, распределение, ретеншн, индексы, производительность, защита данных и отказоустойчивость на стенде не измерены. Для стенда это учебная модель, а не готовое промышленное DWH.
