# Демо-цепочка: продажи и возвраты

Проект, а не заявление о работающей платформе. Сценарий: генератор → Kafka topic `commerce.events.v1` → приём в Greenplum → журнал событий → Vault → звезда → дневной отчёт Superset. Дневной чистый оборот равен сумме отгрузок минус сумма возвратов; отгрузки и возвраты агрегируются независимо. Возврат относится к дате возврата, измерения — к версии на бизнес-дату отгрузки (начало дня UTC).

Слои GP: `demo_stg` — доставка и batch; `demo_ods` — нормализованный журнал событий с replay по `event_id`; `demo_vault` — hubs/links/satellites, события и история; `demo_dm` — SCD-интервалы, отдельные факты, агрегат и представление. Это учебная адаптация паттернов Data Vault, а не заявленная сертифицированная DV 2.0 реализация: разрешение коллизий MD5, multi-source business keys, operational metadata и контроль конкуренции требуют отдельной реализации. Измерения похожи на SCD2, полная корректность на стенде не подтверждена. Политика версий: на сущность и версию допускается ровно один event_id; event_time используется для интервалов измерений, для фактов актуальна наибольшая версия.

## Подготовка изолированного источника

Только после согласования области изменения, резервной копии и проверки отсутствия схем `demo_*`: выполнить `gp/01_schema.sql`, `gp/02_load_vault.sql`, `gp/03_mart.sql` в таком порядке. Доступ в GP, GP6-совместимость, роли и PXF предварительно проверяются оператором. Все применённые версии DDL фиксируются в Git. SQL пока не проверен на живом GP6.

Для отдельной учебной первичной загрузки генератор `gp/04_fixture_sql.py --generator ../webinar-kafka-2026-11-20/commerce_events.py > fixture.sql` формирует локальный SQL; проверить его и выполнить в новой изолированной базе с `psql -v ON_ERROR_STOP=1 -f fixture.sql`, затем `quality/greenplum_checks.sql`. Не передавать учётные данные в аргументах. Данный fixture создаёт фиктивные позиции `fixture.baseline`; это НЕ offset Kafka и не граница миграции. Он запускает первичный расчёт источника, не запускает целевой перенос. Пакет данных и расчёт выполняются в одной GP-транзакции. Нужен один writer; функция не управляет offset Kafka. Одна фиктивная позиция не подходит для реального ingestion.

## Инкременты и граница

Для реального Kafka нужны проверенный consumer/connector, one-writer fencing и durable checkpoint: сначала атомарно записать события и checkpoint в GP, затем коммитить offset; при сбое читать повторно и дедуплицировать по event_id. Текущая SQL-функция не реализует этот consumer и не связывает GP snapshot с Kafka offsets. Фиксация одних лишь времени/offset не гарантирует консистентный срез. Для демо без поддержанного CDC согласовать остановку записи, дождаться обработки, зафиксировать таблицы и offsets по каждой partition и начать читать с корректной следующей позиции; проверить late events, повторы и удаления. Без паузы требуется доказанный snapshot/CDC протокол с транзакционной границей. Начать сохранение delta до потери событий, а применение возможно после baseline; добавление консьюмера нельзя откладывать до момента, когда Kafka retention уже истёк.

## Цель и сверка

`dlh/01_iceberg_ddl.sql` — проект соответствующих таблиц; движок, версия, права и типы не подтверждены. `sales_job.py` — проект расчёта dry-run; publish не означает атомарность нескольких таблиц и требует отдельной реализации fencing, фиксированных input snapshots и безопасной публикации. `quality/target_reconcile.sql` — шаблон проверки по одной согласованной границе с заданными FQN; проверять схему, counts, null, ключи, суммы и bucket hash c одинаковой сериализацией и правилами чисел/NULL/времени. Равенство количества строк само по себе не доказывает равенство данных. GP PK/FK, распределение и индексы не переносятся автоматически в Iceberg; бизнес-инварианты нужно проверять явно.

В каталоге регистрировать только существующие и проверенные сущности: генератор/topic → ingestion → `demo_stg.kafka_event` → `demo_ods.event` → hubs/links/satellites → dimensions и факты → `demo_dm.sales_day` → `v_sales_dashboard` → реальный dataset/dashboard Superset. Для вычисляемых связей указывать DAG/job и колонки, владельца, описание и ссылку на код. То же — для целевого контура после его создания; вымышленные связи не заявлять автоматическим lineage.

## PXF и legacy

PXF — необязательный маршрут чтения внешних файлов или совместимого источника через external table, а не обязательный компонент Kafka ingestion. Для показа использовать отдельную учебную batch-поставку, если фактически установлены и настроены PXF, профиль, сетевой маршрут, безопасные секреты и права; вывести external table как предшественник staging и отметить, что это внешний объект, не копия данных. Не обещать произвольный Kafka-коннектор PXF без проверки версии. В Lakehouse аналог — соответствующий поддерживаемый ingestion/Spark/SQL доступ к источнику и Iceberg.

Кандидат на исключение — отдельно создаваемый устаревший синтетический объект без зависимостей на выбранный отчёт. До решения проверить каталог, SQL-код, логи запросов и потребителей, затем получить решение владельца; отсутствие lineage не доказывает неиспользование. Объект пока не создан.
