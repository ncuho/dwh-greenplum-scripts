# Синтетическое хранилище СНГ на Greenplum

Рабочий источник для демонстрации миграции в Lakehouse: **85 логических таблиц, 527 колонок**, 7 бизнес-витрин, SQL/PLpgSQL-функции и настоящий materialized view. Проверено на оригинальном upstream Greenplum 6.26.2 / PostgreSQL 9.4.26 с двумя primary-сегментами: локальная сборка официального архивного исходного кода, не Yandex-форк и не готовый вендорский binary Broadcom. Это синтетический учебный стенд, не данные и не действующая архитектура ПАО «Сургутнефтегаз».

46 таблиц `ods`/`mart` сохраняют схему и значения существующего синтетического Lakehouse-источника. Дополнительно созданы 34 бизнес-таблицы `ref/stg/dds/dm` и 5 таблиц `ctl`. Исходные 46 таблиц Lakehouse при сборке не изменялись. В данном репозитории нет выгрузки строк, внутренних адресов, сертификатов и ключей. Без авторизованных исходных снимков полный стенд не воспроизводится; одного клонирования недостаточно.

Измерено: 38 417 строк в 46 зеркалах; 200 скважин; 2 400 исходных скважино-месяцев; 73 000 скважино-дней; 1 752 000 телеметрических скважино-часов. Все 85 таблиц заполнены, включая контрольные. Точные числа по каждой таблице — `metadata/observed-row-counts.json`. Размеры описывают проверенный экземпляр, а не автоматически любой повторный запуск.

Выполнено: 46/46 зеркал совпали по значениям, включая IEEE754 DOUBLE; 143/143 проверки данных прошли; 12/12 внесённых дефектов заблокированы; повторный расчёт 7 витрин дал 0 отличающихся строк по двустороннему `EXCEPT ALL`. Проверки дефектов и повторного расчёта откатываются.

## Как собрать новый экземпляр

Нужны Greenplum 6.26.2, `psql`, Python 3.9+, отдельная пустая БД и локальный libpq service (`~/.pg_service.conf`, права 0600). Настройте `PGSERVICE` на неё; пароли/ключи храните локально штатными средствами libpq. Установку GP, сеть и сертификаты данный репозиторий не автоматизирует.

```bash
export PGSERVICE=sng_demo
psql -X -v ON_ERROR_STOP=1 -f sql/00_schema.sql
python3 scripts/load_mirrors.py /path/to/authorized-private-snapshots
psql -X -v ON_ERROR_STOP=1 -f sql/10_build_synthetic.sql
psql -X -v ON_ERROR_STOP=1 -f sql/20_logic.sql
psql -X -v ON_ERROR_STOP=1 -f sql/21_batch_functions.sql
psql -X -At -v ON_ERROR_STOP=1 -f sql/30_quality.sql > quality.jsonl
psql -X -v ON_ERROR_STOP=1 -f sql/40_negative_tests.sql
psql -X -v ON_ERROR_STOP=1 -f sql/41_idempotence.sql
python3 scripts/record_validation.py /path/to/authorized-private-snapshots quality.jsonl
python3 -m unittest discover -s tests -v
```

Порядок существенен: `20` создаёт первый run, `21` второй; `41` проверяет повтор второго run. Начальные DDL/COPY/генератор предназначены только для пустой БД, **не идемпотентны**. Повторяемый рабочий пересчёт: `SELECT etl.run_daily_batch(1, DATE '2025-01-01', DATE '2026-01-01', 2);`. Это фиксированный учебный пакет за 2025 год; интерфейс не заявлен как универсальный промышленный загрузчик.

В `30_quality.sql` каждая JSON-строка должна иметь `errors=0`, а число результатов —143; `record_validation.py` проверяет эти условия и заполняет control-таблицы. Отдельно убедитесь, что все 12 результатов `40` имеют `blocked=t`, а `41` возвращает0. Успешный код выхода `psql` сам по себе не доказывает отсутствие ошибок в данных. Полная битовая проверка оригинального удалённого источника выполнена отдельно; публичный загрузчик не получает доступ к нему.

После сборки выполните `ANALYZE` таблиц и `ANALYZE ROOTPARTITION` пяти partitioned roots. Это требуется для осмысленных планов GPORCA, не является оптимизацией под промышленную нагрузку.

## Контракт исходных файлов

Каталог содержит 46 файлов `<schema>.<table>.json`, только для assets класса `exact_existing_mirror` в `metadata/asset-manifest.json`. Структура каждого:

```json
{"table":"ods.<имя_таблицы>","snapshot_id":"<фактический_snapshot_id>","columns":["<колонки_в_порядке_manifest>"],"rows":[["<значения>"]]}
```

Имена, порядок и типы — из manifest. `NULL` — JSON null; строки и даты — строки; DOUBLE — JSON number без предварительного округления. Загрузчик сохраняет точное значение Python binary64 через длинное десятичное представление для COPY, экранирует табуляции/переводы строк/обратные слеши, блокирует непустые целевые таблицы. Снимки нужны по каждой таблице; это **не** общий транзакционный срез всех таблиц. Требуются именно исходные синтетические данные согласованного кейса: генератор привязан к 200 скважинам и 12 месяцам 2025 года. Произвольные входные данные потребуют изменения контракта.

## Что нельзя интерпретировать буквально

- Физическая единица старых `oil_volume/gas_volume/water_volume` не установлена. Новая суточная добыча — числовое распределение в `legacy units`, без переименования в тонны/м³. Месячные суммы сохраняются до6знаков; сравнение с DOUBLE использует допуск `1e-6 + 1e-12*abs(source)`.
- Новые кПа/°C/мм/с/%/кВт·ч/RUB — явные синтетические единицы. Отгрузки в м³ — независимый синтетический сценарий, не конверсия legacy oil.
- Новые даты/наивные timestamp интерпретируются как UTC. Для оригинальных наивных timestamp зона неизвестна и не изменена. Исходный `workrecord.time` не переводится в часы без установленной единицы; `resolutiontime` описан в минутах.
- STG создан генератором из DDS для начальной демонстрации формата событий. Постоянный ingestion STG→DDS, CDC и расписание здесь не развёрнуты. Не рисуйте обратную фактическому bootstrap lineage.
- Связь service→well назначена синтетически и имеет `is_causal_evidence=false`. Это не доказательство влияния IT-инцидентов на добычу.
- SCD2 использует полуоткрытые интервалы. Пересекающийся downtime **отклоняется**; универсального алгоритма объединения произвольных пересечений нет.

## Миграционные примеры

`docs/migration-mapping.md` объясняет, что переносится, что перепроектируется и почему GP distribution/indexes не переводятся в Iceberg один к одному. `metadata/dependencies.json` фиксирует фактические зависимости вычислений, а FK-подобные связи manifest — только связи модели.

`migration/production-wave.cde.sql` — **неисполненный кандидат** преобразования первой волны, не подтверждённая миграция. Требуются отдельные target tables, проверка совместимости установленного CDE/Iceberg, сверка данных и бизнес-метрик. Многотабличная транзакция GP не превращается в общую транзакцию Iceberg; публикация согласованного набора требует внешнего release protocol. `VALIDATED_DEMO_NO_CUTOVER` означает проверенный источник, не состоявшееся переключение потребителей и не «без простоя».

На GP реально проверены heap, btree, bitmap по TEXT, AO/AOCO+zlib, hash/random/replicated distribution, месячные partition+default, exchange с validation, sequence, domain, enum, JSON, temp table, allowlisted dynamic SQL и materialized view. Enum не имеет нужного bitmap opclass; индекс перенесён на TEXT. Resource manager — queue. Внешний gpfdist runtime, PLPython, native CDC, GPCC и resource groups не заявляются как развёрнутые.
